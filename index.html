How frontier models decode

What is publicly known about how the big LLMs are laid out across accelerators while they generate tokens. Model cards say one 8-GPU server. The deployments that labs have disclosed are often far wider.

Each row is one model's decode instance: the accelerators that together produce its next token. Blue rows are what model cards and framework recipes prescribe. Gold rows are deployments that a lab, or a framework team working with it, actually described. A line spans a stated range, for example a minimum unit and a larger benchmarked one. The closed labs publish neither.

  • Two regimesOpen-weight recipes fit one server at TP4–TP8. Disclosed large-MoE deployments run decode as one instance of 32–320 accelerators, with experts spread thin and attention run separately on every device.
  • The reason is arithmeticDecode is memory-bound until each weight is reused by roughly 280 tokens per step. An MoE expert sees only k/E of the batch, so it needs ~32× more.
  • Closed labs say almost nothingOpenAI, Anthropic, Google and xAI name chips, never replica sizes. The only closed-model layout on record is the unconfirmed 2023 GPT-4 leak.

01Why decode is a different problem

Prefill reads the whole prompt at once, so the matrix multiplies are big and the chip is busy. Decode produces one token per sequence per step. Each step must still stream every active weight, plus every sequence's KV cache, out of memory. At small batch the chip spends its time waiting on bytes, not doing arithmetic.

Batching reuses each weight read across many tokens, so utilisation climbs with batch until the critical batch, where compute takes over. For a mixture-of-experts model, each expert only sees the tokens routed to it, which pushes the knee out by E/k. That is the whole reason big MoEs are served on big pools of accelerators. Numbers from the JAX scaling book; deployment points from DeepSeek and Moonshot disclosures.

02Four ways to split a model

Every deployment below is a combination of these four. What differs is what each device holds and what has to travel between devices on every step.

Colours are fixed for the rest of the page: blue dense weights, gold KV cache, green experts, red communication, violet prefill.

03The default: one server, tensor-parallel 8

Almost every open-weight model card targets this. Eight GPUs share one NVLink switch, every GPU holds an eighth of every layer, and two all-reduces per layer stitch the pieces back together. With grouped-query attention's 8 KV heads, each GPU stores exactly one head's cache, so TP8 is also the natural ceiling.

The same eight GPUs cover the whole latency–throughput range. Meta reports Llama 4 Maverick at about 4 ms per token at batch 1 on 8 H100s, and NVIDIA's B200 record of 1,038 tok/s for one user came from TP8 with EAGLE-3 speculation. The same B200 server at large batch peaks at 72,000 tok/s. Meta runs its decode hosts separately from its prefill hosts (§07).

04The old wide layout: deep pipelines

Before MoE-aware serving, the way to fit a huge model was to cut it into layer stages across nodes. The only per-replica layout ever reported for a closed frontier model is of this kind: the 2023 GPT-4 leak. Pipelining fits memory but does not make a single token faster, because every token still visits every stage in turn.

Reported by SemiAnalysis in July 2023 and never confirmed by OpenAI. Meta's Llama 3.1 405B in BF16 is a small first-party example of the same idea: TP8 within each node and PP2 across 2 nodes (16 H100s). In FP8 it fits one node and the pipeline goes away.

05On TPUs: shard weights on two axes of a torus

Google's published recipe for decode, from Pope et al., served PaLM 540B on 64 TPU v4 chips. Instead of slicing each weight one way, it is sliced along two torus axes, which keeps communication small as the chip count grows. Decode always uses this "2D weight-stationary" layout, because the batch in tokens is small.

Gemini is a sparse MoE served on TPUs with prefill/decode disaggregation and speculative decoding. Google has not disclosed chips per replica. The current TPU for serving, TPU 8i, was built around MoE all-to-all traffic, with a "Boardfly" topology that reaches 1,024 chips in at most 7 hops.

06The shape of the KV cache decides the attention layout

Batch only helps if the KV cache fits, so bytes per token matter. They also decide how attention can be split. GQA's 8 heads split cleanly over 8 GPUs. MLA, used by DeepSeek and Kimi, compresses KV into one shared latent: tensor-parallel attention would copy that latent onto every GPU. So these models run attention data-parallel, with each GPU keeping its own sequences.

At DeepSeek's production average of ~5,000 tokens of context, one sequence holds ~350 MB of KV. Eighty-eight sequences per GPU is ~31 GB, which fits on an 80 GB H800 only because each GPU holds just three experts per layer. Google reached the same answer for PaLM's multi-query attention in 2022: sharding KV by batch instead of by head raised the maximum context at batch 128 from 660 to 43,000 tokens.

07Wide expert parallelism with data-parallel attention

This is the layout DeepSeek runs in production and documents in the most detail. Every GPU runs attention for its own ~88 sequences, and holds just 2 routed experts and 1 shared expert per layer. After attention, each token is shipped to its 8 chosen experts, wherever they live, and the results are shipped back. One decode instance is 18 nodes, 144 H800s.

Figures from DeepSeek's Day-6 disclosure (Feb 2025): a decode unit "spans 18 nodes", EP144 / DP144, with 32 redundant experts (144 × 2 = 256 + 32). The fleet averaged 226.75 nodes over the day. The sequences per GPU figure is derived from DeepSeek's token volumes. Every dispatch and combine crosses InfiniBand, so DeepSeek overlaps communication with compute using two micro-batches and a 5-stage pipeline.

The DeepSeek lineage, from one node to a supernode

Each square is one accelerator, and each column of eight is one server. The V3 report's 320-GPU design used 4-way tensor-parallel attention. Production dropped it: with MLA, TP4 would have stored every latent four times. DeepInfer, open-sourced on 20 October 2026 as DeepSeek's production engine, keeps the same idea on one NVLink-class supernode. Others run the same pattern: Kimi K2 decodes on 96 H200s at 480 sequences each, and Huawei serves DeepSeek-R1 on 160 Ascend 910Cs at EP320.

08Prefill and decode on different machines

Prefill wants few GPUs doing big matmuls. Decode wants as many sequences as the KV pool can hold. Running both on the same GPUs makes each worse, so disaggregation is now standard wherever labs describe their stack: DeepSeek, Meta, Moonshot, Huawei, Meituan, Baidu and, per SemiAnalysis, Gemini. The prompt's KV cache is computed on a prefill GPU and shipped across.

The ratio follows the workload: long prompts with short answers need more prefill, and long reasoning traces need more decode. DeepSeek's figure is derived from its daily token volumes and per-node throughput. As decode instances have grown, prefill instances have shrunk; DeepSeek's went from 32 GPUs to 2–8.

09Going further: attention and experts on different machines

Inside decode, attention and the FFN also want different things. Attention holds KV and grows with context. Experts hold weights and grow with batch. Attention–FFN disaggregation puts them on separate pools and bounces micro-batches between them, so neither pool sits idle.

With three or more micro-batches in flight, the attention pool works on one while the expert pool works on another. The split pays only when the two stage times match: vLLM on Ascend found 48 attention to 16 FFN devices 5% slower than plain EP64, but 64 to 16 was 11% faster.

10Why rack-scale hardware matters for decode

Wide EP sends two all-to-alls per MoE layer, about 120 per forward pass for DeepSeek-R1. Inside an NVLink domain that traffic is cheap. Once it leaves the server, each GPU has about 18× less bandwidth. Hardware for serving MoE models is therefore built around ever larger scale-up domains.

On GB200 NVL72, TensorRT-LLM gets up to 1.8× more tokens per GPU at EP32 than at EP8. In SemiAnalysis's runs the gap to 8-GPU B200 servers opens exactly where B200 must take EP across the network. Two-batch overlap, essential on InfiniBand, was switched off inside NVL72 because communication became cheap.

11Every deployment is a point on one curve

The same hardware can serve many users slowly or a few users fast. As the per-user speed target rises, the batch shrinks and tokens per GPU fall 10–30×. Which parallel layout wins changes along the way.

DeepSeek-R1 in FP4, 1K tokens in and 1K out, disaggregated, with multi-token prediction (SemiAnalysis InferenceX, May 2026). Points compare the two systems at matched speeds per user; throughput figures from other sources on this page are measured under different settings and are not comparable to these. Past ~300 tok/s per user, GPUs give way to SRAM machines: Cerebras serves OpenAI's Codex-Spark at over 1,000 tok/s, and NVIDIA licensed Groq's LPU design for its decode racks.
